ShopStream داشبورد تحلیل بلادرنگی است که برای یک خرده‌فروش با سه فروشگاه آنلاین ساختم — دو فروشگاه منطقه‌ای و یک فروشگاه بین‌المللی. پیش از ShopStream، «تحلیل» در این شرکت یعنی آیین صبحگاهی کار با صفحه‌گسترده؛ پس از آن، همان آدم‌ها سفارش‌ها را زنده تماشا می‌کردند و یک فروش فوریِ در حال خراب‌شدن را همان ساعت پیدا کردند. این، روایت کامل ماجرا است: چه چیزی خراب بود، معماری را چطور انتخاب کردم، چه چیزی منتشر شد و اعدادِ نود روز بعد چه می‌گفتند.

## مسئله

سه فروشگاه این خرده‌فروش روی دو پلتفرم مختلف اجرا می‌شدند و هیچ‌کدام گزارش‌گیریِ عبورکننده از مرز فروشگاه‌ها نداشتند. وضع موجود، خروجی CSV شبانه‌ی هر پلتفرم و به‌هم‌دوختن دستیِ آن‌ها در اکسل بود، هر صبح.

این فرایند به چهار شکل مجزا شکست می‌خورد:

- **داده همیشه کهنه بود.** تا کسی اعداد را می‌خواند، آنها دیروز را توصیف می‌کردند. فروش‌های فوری — همان لحظه‌هایی که دقیقه‌ها اهمیت دارند — تمام می‌شدند پیش از آنکه کسی ببیندشان.
- **ساعت‌های انسانی می‌بلعید.** دو ادمین تقریباً هر صبح حدود ۹۵ دقیقه صرف مونتاژ گزارش می‌کردند، پیش از آنکه اصلاً بتوانند به آن واکنش نشان دهند.
- **مشکلات مرجوعی و موجودی با تأخیر روزها پیدا می‌شدند.** یک دسته کالای معیوب که در دو فروشگاه فروخته شده بود، سه روز طول کشید تا در صفحه‌گسترده‌ی ادغام‌شده دیده شود، چون داده‌های مرجوعی در خروجی جدا بودند که هیچ‌کس روزانه تطبیقش نمی‌داد.
- **در نهایت هم کسی به اعداد اعتماد نداشت.** مُهرهای زمانی، ارزها و منطقه‌های زمانی دستی نرمال می‌شدند؛ یعنی هر ناهنجاری، اول یک راستی‌آزمایی مجدد راه می‌انداخت پیش از آنکه کسی باورش کند.

درخواستی که گرفتم روی کاغذ فروتنانه بود — «یک داشبورد» — اما نیاز واقعی تیزتر از آن بود: تصمیم‌ها درباره‌ی قیمت‌گذاری، تبلیغات و موجودی، ۲۴ ساعت کور گرفته می‌شدند و کسانی هم که می‌گرفتند، این را می‌دانستند.

## فرایند

بیشترِ زمان مهندسی من پیش از نوشتن حتی یک خط کدِ محصول صرف می‌شود؛ این پروژه هم استثنا نبود.

### ممیزی جریان رویدادها

پیش از هر طراحی، دو هفته رویدادهای سه فروشگاه را با یک جمع‌آوری‌کننده‌ی سبک ثبت کردم. به شکل واقعیِ داده لازم بود، نه شکل تصوری‌اش: نوع‌های واقعی رویداد، حجم واقعی، رفتار انفجاری واقعی در زمان تبلیغات. ممیزی حدود ۵۰ هزار رویداد در روز در اوج نشان داد — عمدتاً `page.view` و `cart.updated` — با نمای انفجاری واضح: یک فروش فوری می‌توانست نرخ رویداد را ظرف چند دقیقه سه برابر کند. همین یک واقعیت، چند معماری را کنار گذاشت که در بار متوسط خوب کار می‌کردند و در اوج فرو می‌پاشیدند.

### انتخاب push به‌جای pull

طرح بدیهی — داشبوردی که هر چند ثانیه یک API را poll کند — اولین چیزی بود که رد کردم. با چند کاربر ادمین و چند ویجت، polling ساده‌لوحانه کوئری‌ها را در «تعداد کاربر ضربدر نرخ تازه‌سازی» ضرب می‌کند و هر ویجت تصویری کمی متفاوت از «اکنون» نشان می‌دهد.

سه transport را جدی مقایسه کردم: polling با بازه‌ی کوتاه، Server-Sent Events و WebSocket. WebSocket به سه دلیل برنده شد: یک اتصال به‌ازای کلاینت، مستقل از تعداد ویجت‌ها؛ دوسویه بودنِ واقعی، که به کلاینت اجازه می‌داد دامنه‌ی اشتراک خودش را محدود کند (کاربری که صفحه‌ی قیف را می‌بیند نباید جریان کامل رویدادها را دریافت کند)؛ و مدیریت تمیز backpressure در سرور. یک مسیر جایگزین SSE را هم برای تعداد انگشت‌شمار پراکسی شرکتی که اتصال‌های WebSocket طولانی را خراب می‌کنند، نگه داشتم.

### طراحی مدل داده

تصمیم ساختاری دوم، **ذخیره‌ساز رویدادِ فقط‌الحاقی** (`append-only`) بود. رویدادها واقعیت‌اند؛ هرگز به‌روزرسانی نمی‌شوند، فقط حاشیه‌نویسی می‌شوند. رویدادهای خام در جدول `events` پستگرس با پاکت تایپ‌شده و محموله‌ی JSONB فرود می‌آیند و اعداد تجمیعی داشبورد از جداول rollup پیوسته می‌آیند، نه از `GROUP BY` سرِ وقت روی میلیون‌ها سطر.

این تفکیک — واقعیت‌های خامِ تغییرناپذیر، تجمیع‌های مشتق — کل سیستم را قابل‌مدیریت کرد. بازسازی یک rollup بعد از یک باگ، تابعی خالص از لاگ رویدادهاست؛ هیچ‌چیز گم یا دوبار شمرده نمی‌شود، چون خط لوله‌ی غنی‌سازی بر اساس ساختار idempotent است.

## راه‌حل

سیستم منتشرشده سه بخش متحرک دارد: سرویس دریافت، هسته‌ی PostgreSQL + Redis و داشبورد Next.js.

سرویس دریافت یک اپلیکیشن کوچک Node.js است که رویدادها را از فروشگاه‌ها می‌گیرد، هر محموله را با پاکت TypeScript سخت‌گیرانه اعتبارسنجی می‌کند و به Redis Stream می‌راند. Redis نقش ضربه‌گیر را بازی می‌کند — اگر PostgreSQL حین بازسازی rollup کند شود، استریم بافر می‌کند و هیچ‌چیز نمی‌افتد. یک consumer پس‌زمینه استریم را به PostgreSQL تخلیه و رویدادها را به کلاینت‌های WebSocket متصل، fan-out می‌کند.

اعتبارسنجی پاکت عمداً پارانویایی است، چون ذخیره‌ساز فقط‌الحاقی، زباله را دائمی می‌کند:

```ts
interface EventEnvelope<T extends EventName = EventName> {
  name: T;
  storeId: StoreId;
  occurredAt: string; // ISO 8601, set by the client
  receivedAt: string; // set by the server, never trusted from outside
  payload: EventPayload<T>;
}

function assertValidEnvelope(input: unknown): EventEnvelope {
  if (typeof input !== "object" || input === null) {
    throw new InvalidEventError("envelope must be an object");
  }
  const candidate = input as Partial<EventEnvelope>;
  if (!isEventName(candidate.name)) {
    throw new InvalidEventError(
      `unknown event name: ${String(candidate.name)}`,
    );
  }
  if (!isStoreId(candidate.storeId)) {
    throw new InvalidEventError("unrecognized storeId");
  }
  if (!isIsoTimestamp(candidate.occurredAt)) {
    throw new InvalidEventError("occurredAt must be ISO 8601");
  }
  // The payload is validated per event name; anything that fails is
  // logged to a dead-letter table and never enters the event store.
  return parsePayload(candidate as EventEnvelope);
}
```
